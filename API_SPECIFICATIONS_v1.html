1. API Overview

Base URL
https://api.transparency.internal/v1

Note: All endpoints require HTTPS/TLS 1.2+. Plain HTTP is rejected with 403 Forbidden.

System Architecture

The API is organized into 6 logical modules:

Module Base Path Purpose
Jobs /jobs Job positions, evaluations, categories
Employees /employees Employee data (pseudonymized), salary components
Analysis /analysis Pay gap calculations, drill-down, trends
Justifications /justifications Gap justifications, workflow approvals
Reports /reports Official exports (PDF, XML, CSV)
Audit /audit Immutable logs, compliance verification
Global Standards
  • Request Format: JSON (application/json)
  • Response Format: JSON with standardized envelope
  • Timestamps: ISO 8601 UTC (e.g., 2026-05-13T14:30:00Z)
  • Pagination: offset/limit model (default limit: 50, max: 500)
  • Sorting: Multi-field sort via ?sort=field1,-field2 (- for descending)
  • Filtering: Query string parameters with operators (?field[gte]=100)
  • Rate Limiting: 1000 requests/hour per API key (429 Too Many Requests)
  • Idempotency: All state-changing requests require Idempotency-Key header

2. Authentication & Authorization

Authentication Method

All endpoints (except /health) require JWT Bearer token authentication.

Request Header:
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

JWT is obtained via POST /auth/login with username/password or SAML2 SSO endpoint.

JWT Token Structure
{ "sub": "user_id_12345", "name": "John Smith", "email": "john@company.internal", "roles": ["hr_specialist"], "department": "HR", "department_id": "dept_001", "permissions": ["read:jobs", "write:salaries", "read:analysis"], "iat": 1715590200, "exp": 1715676600, "aud": "transparency-api" }
Role-Based Access Control (RBAC)
Role Permissions Data Access Scope
HR Specialist All create/read/write/delete for Jobs, Employees, Salary Data. Workflow initiation. All departments in company
Manager Read jobs, employees (own dept), approve justifications. Cannot delete or bulk import. Own department only
Compliance Officer Read all. Validate justifications. Generate official reports. Access audit logs. All departments (read-only)
Employee Read own salary info (pseudonymized). Submit Art. 10 requests. View own justifications. Own salary record only
CFO Read reports. View cost analysis. Dashboard metrics. Aggregate company data only
Authorization Header Requirements
Authorization Context Headers (on every request):
X-User-Role: hr_specialist
X-Department-ID: dept_001
X-User-ID: user_12345

Enforcement: API enforces role+department at business logic layer, not just UI layer. All filtering is server-side (immutable). Unauthorized access returns 403 Forbidden.

3. API Standards & Conventions

Standard Request Envelope
{ "action": "POST", "resource": "job", "timestamp": "2026-05-13T14:30:00Z", "request_id": "req_abc123xyz", "data": { /* endpoint-specific payload */ }, "metadata": { "idempotency_key": "idem_key_12345", "version": "1.0" } }
Standard Response Envelope (Success)
{ "status": "success", "code": 200, "data": { /* response payload */ }, "meta": { "request_id": "req_abc123xyz", "timestamp": "2026-05-13T14:30:01Z", "execution_time_ms": 245 } }
Standard Response Envelope (Error)
{ "status": "error", "code": 400, "error": { "type": "validation_error", "message": "Invalid salary component type", "details": [ { "field": "component_type", "issue": "must be one of: BASE, BONUS, BENEFITS, OTHER", "value": "INVALID" } ] }, "meta": { "request_id": "req_abc123xyz", "timestamp": "2026-05-13T14:30:01Z" } }
Pagination Response Format
{ "status": "success", "data": [ /* array of items */ ], "pagination": { "offset": 0, "limit": 50, "total": 342, "has_more": true, "next_offset": 50 } }
Filtering & Search Operators
Operator Example Meaning
[eq] ?status[eq]=active Exact match
[ne] ?status[ne]=deleted Not equal
[gte] ?salary[gte]=3000 Greater than or equal
[lte] ?salary[lte]=5000 Less than or equal
[in] ?status[in]=active,pending In list
[contains] ?job_title[contains]=Manager Substring match (case-insensitive)
[date_gte] ?created_at[date_gte]=2026-01-01 Date on or after

4. Job Management Endpoints

POST /jobs
Create a new job position

Required RBAC Role:

hr_specialist

Request Body:

{ "job_code": "JOB-001", "job_title": "Senior Software Engineer", "department_id": "dept_001", "description": "Design and develop backend services", "equal_value_category": "IT_TECHNICAL", "salary_band_min": 3500, "salary_band_max": 6000, "approved_by_manager": true }

Response (201 Created):

{ "status": "success", "code": 201, "data": { "job_id": "job_12345", "job_code": "JOB-001", "job_title": "Senior Software Engineer", "created_at": "2026-05-13T14:30:00Z", "created_by": "user_001", "version": 1, "status": "draft" } }

Validation Rules:

  • job_code: Unique, alphanumeric + hyphen, max 50 chars, required
  • job_title: Required, max 200 chars
  • department_id: Must exist, required
  • equal_value_category: Required, must be valid EVC code
  • salary_band: salary_min < salary_max, both positive decimals
Audit Logging: Job creation is logged with user_id, timestamp, and full payload. Cannot be deleted or tampered with.
Directiva 2023/970 Art. 4: Job must have objective criteria defined. This endpoint only creates the job definition; criteria are assigned via PUT /jobs/:id/evaluation.

Error Responses:

400 Invalid job_code format or duplicate
403 Insufficient RBAC role
404 Department not found
500 Database transaction failed

POST /jobs/:job_id/evaluation
Evaluate job on 7 weighted criteria (per Directiva Art. 4)

Required RBAC Role:

hr_specialist

Request Body:

{ "criteria_scores": { "competencies": 90, "effort": 85, "responsibility": 88, "conditions": 75, "complexity": 92, "autonomy": 80, "impact": 70 }, "evaluation_notes": "Evaluated by job analysis committee" }

Calculation (Server-Side):

Weighted Score = Σ(score × weight)

Criterion Weight
Competencies 25%
Effort 15%
Responsibility 25%
Working Conditions 10%
Complexity 10%
Autonomy 10%
Impact 5%

Validation Rules:

  • Each score: integer 0-100, required
  • Weights are immutable and hardcoded (not user-configurable)
  • Equal Value Category auto-assigned based on weighted_score ranges

Response (201 Created):

{ "status": "success", "code": 201, "data": { "evaluation_id": "eval_98765", "job_id": "job_12345", "weighted_score": 84.5, "equal_value_category": "IT_TECHNICAL", "status": "approved", "evaluated_at": "2026-05-13T16:00:00Z" } }
Directiva 2023/970 Art. 4: Jobs must be evaluated using objective, non-discriminatory criteria. This endpoint implements the weighting specified in Art. 4(2).
Audit Logging: All evaluation scores and weighted calculations are logged. Immutable historical record maintained.

Column Type Required Example

5. Employee & Salary Data Endpoints

POST /employees/bulk-import
Import employees with irreversible pseudonymization (per GDPR Art. 32 & TS-M2-001)

Required RBAC Role:

hr_specialist

Request (multipart/form-data):

{ "file": "employees_2026_05.csv", "format": "csv", "gender_column_index": 4, "salary_column_index": 5 }

Input CSV Format:

Column Type Notes
employee_id string Internal ID, max 50 chars
employee_name string Pseudonymized server-side using irreversible SHA-256
gender enum M or F only (required for pay gap analysis)
job_code string Must exist, linked to job evaluation
base_salary decimal Gross monthly, must be > 0

Pseudonymization Process (Server-Side):

Algorithm: One-way SHA-256(employee_name + salt)
Output: EMP_XXXXX (deterministic, same input always produces same pseudonym)
Irreversibility: No reverse mapping stored. Cannot decrypt pseudonym back to name.
Data Preserved: Gender, salary, job assignment preserved; only name anonymized.
GDPR Compliance: Meets Art. 32 pseudonymization requirement. No PII stored in salary tables.

Response (202 Accepted):

{ "status": "success", "code": 202, "data": { "import_id": "imp_emp_12345", "total_rows": 250, "status": "processing", "pseudonym_sample": "EMP_a7f3b9c1", "created_at": "2026-05-13T14:30:00Z" } }

Validation Rules:

  • Salary > 0 and < 500,000 (sanity check)
  • Gender is M or F only
  • Job code must be approved before employee link
  • No duplicate pseudonyms across imports (idempotency check)
  • Atomic: all rows or rollback
Audit Trail: Import logged with row count, user_id, file hash. Pseudonymization algorithm and salt logged (for compliance verification, not reversal).

Add salary component to employee (base, bonus, benefits, other)

Type Description Included in Gap Calc
BASE Base salary (immutable once approved) Yes
BONUS Performance or annual bonus Yes
BENEFITS Non-cash benefits (car, insurance, etc.) Yes (monetized value)
OTHER Other compensation No (excluded from pay gap)

Validation Rules:

  • Amount: positive decimal, max 2 decimal places
  • effective_date ≤ valid_until (if both provided)
  • Type must be one of: BASE, BONUS, BENEFITS, OTHER
  • Version history maintained (immutable previous versions)
Audit Logging: All salary component changes logged with before/after values, user_id, timestamp.

6. Gap Analysis Endpoints

POST /analysis/calculate-pay-gap
Calculate aggregate pay gap by gender and equal value category (per TS-M3-001)

Required RBAC Role:

hr_specialist, compliance_officer

Request Body:

{ "period": "2026-05", "include_categories": ["IT_TECHNICAL", "ADMINISTRATIVE"], "minimum_sample_size": 5 }

Gap Calculation Formula:

Formula: gap_percent = ((avg_salary_M - avg_salary_F) / avg_salary_F) × 100
Rounding: 1 decimal place (e.g., 5.3%)
Flagging: Gaps ≥ 5% automatically flagged for justification (Art. 5)
Sample Size: Minimum N per group (default 5, configurable)

Response (200 OK):

{ "status": "success", "code": 200, "data": { "analysis_id": "analysis_12345", "period": "2026-05", "calculation_timestamp": "2026-05-13T14:30:00Z", "gap_results": [ { "equal_value_category": "IT_TECHNICAL", "sample_male": 45, "sample_female": 35, "avg_salary_male": 4850.50, "avg_salary_female": 4625.00, "gap_percent": 4.9, "flagged": false, "status": "no_action_required" }, { "equal_value_category": "ADMINISTRATIVE", "sample_male": 12, "sample_female": 28, "avg_salary_male": 2950.00, "avg_salary_female": 2650.00, "gap_percent": 11.3, "flagged": true, "status": "requires_justification" } ], "summary": { "total_gaps_calculated": 2, "gaps_flagged": 1, "overall_avg_gap": 8.1 } } }
Directiva 2023/970 Art. 5: Pay gaps ≥ 5% must be justified. This endpoint identifies all flagged gaps requiring Art. 5 justification.
Audit: Calculation logged with period, formula used, sample sizes, results, user_id, timestamp.

Characteristics:

  • Navigation: Clients can traverse tree for data exploration

7. Justifications Endpoints (Directiva Art. 5)

POST /justifications
Create justification for flagged pay gap (≥5%) - per Directiva Art. 5 & TS-M4-001

Required RBAC Role:

hr_specialist

Request Body:

{ "gap_id": "gap_12345", "equal_value_category": "ADMINISTRATIVE", "template_type": "seniority", "description": "Pay gap due to different tenure distribution: 80% of females hired in last 2 years, 40% of males", "supporting_files": ["file_id_123", "file_id_124"], "effective_date": "2026-05-13" }

Justification Templates (Art. 5 Factors):

Template Description
seniority Difference in tenure/years of service
performance Performance metrics, bonus history differences
education Education level, certifications, qualifications
market_rate Market rate differences, skills scarcity
role_change Role changes, promotions, transitions
other Other objective, non-discriminatory factors

Validation Rules:

  • Description: minimum 50 characters (must be substantive)
  • Supporting files: max 5, max 10MB each (PDF, DOCX, XLS preferred)
  • Template type: required, must be from enum
  • Gap must be flagged (≥5%) and not already justified

Response (201 Created):

{ "status": "success", "code": 201, "data": { "justification_id": "just_12345", "gap_id": "gap_12345", "status": "pending_manager_approval", "template_type": "seniority", "workflow_stage": 1, "next_approver_role": "manager", "created_at": "2026-05-13T14:30:00Z", "created_by": "user_001" } }
Directiva 2023/970 Art. 5: Justifications must explain pay gaps ≥ 5% based on "objective, non-gender-based factors." Templates ensure structured collection of Art. 5-compliant factors.
Audit: Justification creation logged with gap_id, description hash, supporting files, user_id, timestamp.
PUT /justifications/:justification_id/approve
Manager approval of justification (workflow stage 1) - per TS-M4-002

Required RBAC Role:

manager

Request Body:

{ "decision": "approved", "comments": "Seniority distribution is well documented", "idempotency_key": "idem_mgr_12345" }

Workflow Stages:

Stage Role Action Next Stage
1 Manager approve / reject / request_revision Stage 2 (Compliance) or back to draft
2 Compliance Officer approve / reject Completed / rejected

Decision Options:

  • approved - Justification is sound, move to next stage
  • request_revision - Send back to HR with required changes

Response (200 OK):

{ "status": "success", "code": 200, "data": { "justification_id": "just_12345", "status": "pending_compliance_approval", "workflow_stage": 2, "next_approver_role": "compliance_officer", "decision_timestamp": "2026-05-13T16:00:00Z", "decided_by": "user_mgr_001" } }

Constraints:

  • Once approved, cannot be modified (locked)
  • Rejection requires mandatory reason (min 50 chars)
  • Revision request routes back to HR for changes
  • All decisions immutably logged with timestamp and user
Audit: Approval decision logged with justification_id, decision, comments, approver_id, timestamp, request_id.

Compliance officer validation against Directiva Art. 5 (stage 2) - per TS-M4-003

Required RBAC Role:

compliance_officer

{ "decision": "approved", "art5_compliance_assessment": { "is_objective": true, "is_non_discriminatory": true, "is_properly_documented": true, "comments": "Seniority factor is objective and well-substantiated" }, "idempotency_key": "idem_co_12345" }

Art. 5 Compliance Validation:

Directiva 2023/970 Art. 5:
✓ Objective criteria (not subjective)
✓ Non-discriminatory (not based on gender, origin, etc.)
✓ Properly documented (evidence provided)

Response (200 OK):

{ "status": "success", "code": 200, "data": { "justification_id": "just_12345", "status": "approved", "gap_id": "gap_12345", "art5_compliant": true, "certificate_generated": true, "certificate_id": "cert_12345", "validated_at": "2026-05-13T16:30:00Z", "validated_by": "user_co_001" } }

Employee information request (Directiva Art. 10) - self-service, 30-day response deadline - per TS-M4-004

Required RBAC Role:

employee

Request Body:

{ "employee_pseudonym": "EMP_a7f3b9c1", "request_type": "salary_comparison", "request_details": "I want to understand my salary vs. others in similar roles" }

Available Request Types:

  • salary_comparison - Compare own salary to equal value category average
  • gap_information - Information about pay gaps affecting own category
  • justification_status - Status of justifications for own category gaps

Response (201 Created):

{ "status": "success", "code": 201, "data": { "request_id": "art10_12345", "employee_pseudonym": "EMP_a7f3b9c1", "status": "submitted", "request_type": "salary_comparison", "deadline": "2026-06-12", "submitted_at": "2026-05-13T14:30:00Z" } }

Auto-Response Content (pseudonymized):

What employee sees:
- Own salary (visible to self)
- Average salary for own equal value category (aggregated)
- Pay gap for own category (if ≥ 5%)
- Justifications for own category gaps (summary, not per-employee details)
Never shows: Other employees' names or individual salaries

Response Deadline:

  • System auto-generates response within 30 days (Art. 10)
  • Notification sent to employee at deadline
  • Response includes pseudonym-coded salary data only
  • Timestamp logged for compliance verification
Directiva 2023/970 Art. 10: Employees have right to request information about own salary and relevant pay gaps. Response must be provided within 30 days in pseudonymized form.
Audit: Request logged with employee_pseudonym, request_type, submission_date, deadline, response_date.

POST /reports/audit-report
GDPR audit report (immutable log, 3-year retention, hash chain) - per TS-M5-004

Required RBAC Role:

compliance_officer

Request Body:

{ "period_start": "2023-05-01", "period_end": "2026-05-13", "format": "html" }

Audit Log Contents:

Entry Fields Immutable?
User Actions user_id, action, resource, timestamp, result Yes (append-only)
Data Changes entity_id, before, after, changed_by, timestamp Yes (append-only)
Access Events user_id, resource, access_type, timestamp, result Yes (append-only)
Reports Generated report_id, user_id, timestamp, hash Yes (append-only)

Immutability Guarantees:

Append-only: New entries added, never modified or deleted
Hash Chain: Each entry includes hash of previous entry (like blockchain)
Tamper Detection: Hash chain validated on every read (breaks if any entry modified)
Retention: 3-year retention (deletion happens automatically after 3 years)
Daily Backup: Audit log backed up daily to separate, read-only storage

Response (200 OK):

{ "status": "success", "data": { "report_id": "audit_12345", "period": "2023-05-01 to 2026-05-13", "total_entries": 15234, "format": "html", "generated_at": "2026-05-13T16:00:00Z", "generated_by": "user_co_001", "hash_chain_valid": true, "earliest_entry": "2023-05-01T08:00:00Z", "latest_entry": "2026-05-13T15:59:00Z" } }

Report Format Options:

  • html - Searchable HTML with filtering
  • csv - Flat CSV for analysis tools
  • json - Structured JSON with hash chain metadata
GDPR Art. 32: Audit logging required for data processing compliance. This report provides the immutable evidence of system usage and data handling.
Audit Recursion: The audit report generation itself is logged in the audit log (meta-audit).

10. Error Handling & Status Codes

HTTP Status Codes
Code Meaning When to Use
200 OK Successful GET, PUT, DELETE
201 Created Successful POST creating resource
202 Accepted Request accepted for async processing (bulk import)
400 Bad Request Invalid input, validation error
401 Unauthorized Missing or invalid JWT token
403 Forbidden Authenticated but insufficient RBAC role/scope
404 Not Found Resource doesn't exist
409 Conflict Resource already exists (duplicate job_code), or workflow state conflict
429 Too Many Requests Rate limit exceeded (1000 requests/hour)
500 Internal Server Error Unexpected server error (log and retry)
503 Service Unavailable Database down or under maintenance
Error Response Structure
{ "status": "error", "code": 400, "error": { "type": "validation_error", "message": "Request validation failed", "details": [ { "field": "salary", "issue": "must be positive", "value": -500 }, { "field": "job_code", "issue": "already exists (duplicate)", "value": "JOB-001" } ] }, "meta": { "request_id": "req_abc123xyz", "timestamp": "2026-05-13T14:30:01Z" } }
Common Error Scenarios
Scenario Status Error Type Action
Invalid JWT 401 auth_error Retry with valid token or login
Manager trying to access other dept 403 rbac_error Verify user role and department assignment
Salary field is negative 400 validation_error Fix input and retry
Job code already exists 409 conflict_error Use different job_code or retrieve existing
Database transaction failed 500 server_error Retry with exponential backoff (with Idempotency-Key)
Rate limit exceeded 429 rate_limit_error Wait and retry (check Retry-After header)
Retry Logic
  • Idempotent requests (POST, PUT with Idempotency-Key): Safe to retry indefinitely
  • Transient errors (500, 503, 429): Retry with exponential backoff (1s, 2s, 4s, 8s, max 32s)
  • Non-idempotent without key: Do not retry (risk duplicate records)
  • Rate limit (429): Check Retry-After header for wait time
